01 / The pieces

Six parts, one loop

Each part does one job. They talk to each other through plain files on disk, so any of them can be read or fixed by hand.

01 / KANBAN

The board

A small web app on my Mac with one JSON file behind it. Columns: inbox, to do, doing, done, later. Every change goes through one command-line tool, board.py, so Claude and I edit the same way.

02 / LIFE-OS

The vault

My private Obsidian vault: business, projects, people, call debriefs, journal, ideas. Each area has an index file that says what lives where.

03 / CLAUDE CODE

The assistant

Claude Code (and sometimes Codex) runs in my terminal and in T3 Code, an app that holds many agent threads side by side. It reads and writes files like a developer would.

04 / SKILLS

The playbook

A private repo of rules and skills: written procedures for capturing a task, debriefing a call, delegating work. A registry decides which skills are available everywhere and which only inside one folder.

05 / RIFF

The build method

My framework for building software with agents in small, checked phases. Another AI model reviews each phase before it counts as done.

06 / MAC MINI

The night shift

A second Mac that runs the agents. It gets the board through file sync and sends back reports and screenshots, never edits to the board itself.

02 / How I work

Deep work first, small stuff in one batch

My attention is the scarce resource. The whole setup exists to protect long, focused blocks and to keep the small things from leaking into them.

VOICE

I dictate, Claude cleans up

I speak to Claude rather than type. Dictation garbles words and names ("my iOS" for "my Life OS"), so Claude reads by sound and context and fixes names from my sources. It only asks when two readings would lead to different actions.

CAPTURE

Tasks appear wherever they come up

A global rule tells Claude: when an action for me clearly emerges in any session (someone waits for my reply, a commitment from a call), add a card to the inbox. It checks the board for duplicates first and tells me the card's title in one line.

CARDS

One card per big piece of work

  • A short title, two to five words, just the action.
  • Steps as bullets, grouped under ## Person or ## Project headings, with sub-steps indented.
  • Finished steps become ✓, shown as checkboxes in the app.
  • A priority from 1 to 4 with a one-sentence reason: 1 earns money or engages a client this week, 4 is "when there's time".
BATCH

One card for small actions

All the tedious bits (a reply, a follow-up, an API key to find, a quick deploy) go into one card called "small batched actions". I clear it at the start of the day or while a long agent run is going, never in the middle of deep work.

WAITING

Blocked cards say what they wait for

A card can be blocked by a person, a dated event or another card. The app lists these under "Waiting", grouped by who or what. A card blocker lifts itself when that card is done; a dated one lifts on its date.

VIEWS

Three ways to look at the board

The board itself, an overview grouped by priority, and "To review", where agent results wait for me. The app is installable as a phone-style app from Chrome and starts on its own at login.

03 / The workflow

The life of one card

From a sentence in a call to approved work. Here's who does what at each step.

  1. 01Me + Claude

    Capture

    After a call, Claude writes a debrief into the vault and proposes tasks. Once I agree, each becomes a card with the debrief attached as a linked document, so the context travels with the task.

  2. 02Claude

    Shape

    Claude finds the big card the action belongs to and adds a step there rather than a new card. It sets the priority, the partner, the product group and the repository the work happens in.

  3. 03Me

    Hand off

    If a card, or one section of it, needs no decision from me, I give it to an agent with "Hand to Claude": which repo, how much thinking effort, and a note on what to leave alone.

  4. 04Agent on the Mac mini

    Work

    At 7 a.m. a scheduled task launches every ready agent, or I click "Launch agent". Each gets its own thread and its own copy of the repo on a separate branch, and commits locally only.

  5. 05Agent

    Report

    It checks its work in a browser, then reports back: two or three sentences "to check", up to three screenshots, what it couldn't test, and any messages it drafted for other people.

  6. 06Me

    Approve

    Approve ticks the finished steps. Refuse sends it back with a word of feedback. "Ask the agent" gives it more to do without throwing away its work. If it stopped on a question, I answer and relaunch.

Why agents don't just finish the job. Pushing code, deploying and messaging people stay with me. Deploys from agent work land in my batch card, and drafted messages wait on the card until I send them.

04 / Finding the project

How Claude knows where to go

Claude doesn't guess. Every request passes through the same three-way split, then a chain of index files that point to the right folder.

STEP 1Sort the requestSoftware work loads the dev workflow and the repo's own instructions. Personal or business requests go to the vault. A neutral question loads nothing private.
STEP 2Read the indexThe "second-brain" skill reads the vault's root index, then only the one area that fits: business, projects, people, journal…
STEP 3Follow the linksThe area index points to the real owner, for example a project folder or a partner's call notes. Names match loosely ("Tackle Box" finds TackleBox).
STEP 4Or askIf no owner fits, Claude asks one targeted question or drops the note in the vault's inbox. It never invents a place.
CARD → REPO

Each card knows its repository

A card stores the absolute path of the repository it's about. When an agent launches, it checks that path is a git repo on the Mac mini, branches from its current branch and works in a separate copy (a git worktree), so the original stays untouched.

CARD → CONTEXT

Each card carries its sources

Cards link to documents: the call debrief, the plan, the synthesis it came from. The app opens them in a reader or in Obsidian, and the agent can read them for context.

REPO → RULES

Each project brings its own instructions

Every repo has an instruction file for agents (CLAUDE.md or AGENTS.md) and sometimes a short "critical context" file that loads automatically when a session starts inside it. So the same agent behaves differently in a client app and in my vault.

SKILLS → SCOPE

Skills appear only where they belong

The skill registry lists a few global helpers (vault routing, dictation cleanup, delegation…) and attaches the others to one folder. The task-capture rule is global, which is why a card can be added from any repo.

05 / RIFF

Building software in checked phases

RIFF is the framework I built for solo development with agents. The kanban can hand a ready RIFF phase straight to an agent.

PLAN

Brief, roadmap, phases

/riff:start interviews me about a new product and writes PROJECT.md (the brief) and ROADMAP.yaml (phases with priorities and prerequisites). /riff:onboard maps an existing app, and /riff:evolve plans a change.

BUILD

Waves

/riff:wave picks the next ready phases, builds them, runs the checks, gets a review, commits and closes each phase. It can run independent phases in parallel, each in its own copy of the repo.

VERIFY

A second model reviews

The agent that builds never grades itself. A model from another provider reviews each phase, and only high or critical findings block. Evidence must match the committed code, and a short plain-language explanation is written after each phase.

STOP

Human checkpoints

In loop mode it keeps going until it hits something only I can do: credentials or access, a check on a third-party service, a destructive target, or a failing validation. Publishing, merging and deploying always need my explicit go.

Kanban meets RIFF. A card can be handed off as a RIFF task with a phase name. The agent then runs that phase with RIFF in autonomous loop mode, inside the card's repository, until it's closed. If RIFF parks, blocks or waits for a decision, the agent reports "stopped" and the card turns into a question for me.

06 / Messages out

Every card has an outbox

Agents often need to tell someone something. They don't send it; they draft it on the card, routed by role, with any useful file attached.

BUSINESS PARTNERSlack + ClickUpWhat's done goes in a Slack message. Marketing and business questions are grouped into one ClickUp task.
INFRASTRUCTURESlackDNS, hosting and Cloudflare questions go to the person who manages our infrastructure.
CONSULTING CLIENTEmail draftWritten as a Gmail draft. I can also send it straight away from the card.
MEBatch cardDeploys and code steps join my small-actions card when I approve.
EDIT

I stay the editor

I can edit any message by hand, or give an instruction ("shorter, and ask about the deadline") and a model rewrites it. Only the messages I tick go out when I approve.

CLICKUP

A shared list, kept in sync

My business partner works in ClickUp. Every 20 seconds a background script syncs our shared list with the board, both ways. Steps I tick get ticked there, and progress that isn't on ClickUp yet is added to the closest existing task, without duplicates. A card only goes to ClickUp if there's something for my partner to do.

07 / Machines & sync

Two Macs, one board

The laptop is where I work. The Mac mini is where agents run. Plain file sync connects them.

MACBOOK

Where the board lives

  • The web app runs at login and restarts if it crashes.
  • The board file sits in my vault, which commits itself to git after each session.
  • Agents that need to control the screen (computer use) wait for my click and run here.
MAC MINI

Where agents run

  • Gets the board through Syncthing, one or two minutes behind.
  • Never writes the board. It only writes report folders with screenshots and files, which sync back.
  • Launching from the laptop goes over SSH to the mini.
MODELS

Right model for the job

Agents run on Claude Opus with an effort level per task: low for a bounded change, medium for a sizeable job, high for a hard diagnosis. Small jobs (rewriting a message, matching a step) go to cheaper, faster models. RIFF picks its own.

THREADS

One thread per task

Each agent gets its own T3 Code thread, so I can open it and read exactly what it did. A morning thread recaps what launched. If a thread ends without a report, the app notices within two minutes and shows its last answer.

08 / Guardrails

What the agents may not do

These rules are in every agent's instructions, not just in my head.

  • No push, merge or deployCommits stay local on the agent's branch until I've looked.
  • No messages sentSlack, email and ClickUp drafts wait on the card.
  • No board edits from the miniOnly the laptop writes the board, so two machines never fight over one file.
  • No decisions for meAnything that needs my judgment, an account or access is left out in the hand-off note, or becomes a blocker addressed to me.
  • No self-grading in RIFFA different model reviews before a phase counts as done.
  • No guessing where things goAn unknown owner gets a question or the inbox, never a made-up folder.

09 / Frequently asked

Common questions

Why a homemade kanban instead of Todoist or Trello?

Because Claude needs to read and write it as easily as I do. It's one JSON file and one command-line tool, with fields that matter to agents: the repository, linked documents, blockers, the agent hand-off and the outbox.

How does Claude avoid creating duplicate cards?

It lists the board before adding anything and checks the steps, not just the titles. If a meeting-agenda card already holds the questions for someone, other cards point to it instead of repeating them.

What does an agent actually get when it starts?

A prompt built from the card: the steps it should do, the hand-off note, the linked documents and the repository. It also gets the rules: work alone in its own copy, commit locally, check in a browser, report with screenshots, and stop and report if it needs me.

What if an agent is wrong?

I refuse with a short reason and it tries again in the same thread, with all its context. Nothing it did has left its branch, so a wrong result costs a review, not a cleanup.

How much do I still do myself?

Decisions, reviews, deploys and anything involving a relationship. The agents take the fixes, checks, tests and first drafts. I see their work as a queue to review, not as a pile of open threads.

Could someone else use this?

There's an open source version of the kanban, Claude Code Kanban, also on this site. The routing, vault and partner rules are personal and stay private.

The short version

Talk. Capture. Delegate. Review.

Everything I say becomes a card in the right place, the boring parts happen overnight, and nothing leaves without my approval.
